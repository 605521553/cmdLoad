# Pata Commands —— 桌面命令管理工具开发需求文档

**文档版本：** 1.0
**目标平台：** Windows 10 / 11（64 位）
**产品定位：** 轻量级、本地优先、AI 辅助的开发者命令管理工具
**开发方式：** 由 AI 编程工具分阶段实现，确保代码可读、模块独立、易于测试和维护。

# 一、项目概述

## 1.1 项目背景

开发者日常使用 Windows PowerShell、CMD、Linux Shell、SSH、Docker、Git、Python 等工具时，会频繁输入或复制大量命令。

这些命令可能具有以下特点：

- 需要频繁使用，但不容易记住完整参数。
- 命令较长，包含多个参数、路径或环境变量。
- 多条命令之间存在顺序关系，需要按照步骤执行。
- 不同操作系统、项目、环境下需要使用不同命令。
- 需要为命令记录执行目的、参数说明及注意事项。
- 命令散落在聊天记录、文档、剪贴板或终端历史中，难以集中检索和维护。

Windows 自带的 Win + V 剪贴板历史可以保存和复制文本，但缺乏长期收藏、树状分类、多步骤编排、注释管理和结构化导出等能力。

因此，希望开发一款专门面向开发者的命令管理桌面应用。

## 1.2 产品目标

实现一款能够长期驻留 Windows 系统托盘的轻量级应用。

核心目标：

1. 像 Win + V 一样快速呼出、查看和复制命令。
2. 支持从剪贴板快速收藏命令，以及手动新增和编辑。
3. 支持目录树、标签和多步骤工作流，方便整理复杂命令。
4. 支持命令卡片颜色、注释、预览和多选复制等操作。
5. 支持用户配置自己的 AI API，自动生成命令解释和注释。
6. 使用结构化数据持久化存储，支持完整备份和导出。
7. 为后续 AI 自动分类、知识检索、MCP 接入等能力预留扩展接口。

**核心原则：命令管理与快速复制是主功能，AI 用于辅助理解与整理，不能让 AI 成为基础功能运行的必要条件。**

## 1.3 目标用户

主要面向：

- 软件开发者
- AI 与深度学习研究人员
- Linux / Windows 开发人员
- DevOps 工程师
- 经常使用 SSH、Docker、Git、Python 等命令行工具的用户

## 1.4 非目标功能

首个正式版本暂不实现：

- 内置终端模拟器。
- 自动执行命令或执行完整工作流。
- SSH 远程终端连接。
- 云端账户及跨设备同步。
- 多用户协作。
- 浏览器插件。
- 完整的自动化脚本运行平台。

这些功能不属于本产品的核心定位。

# 二、功能需求

## 2.1 系统托盘与快捷呼出（P0）

### 功能要求

1. 应用支持后台常驻 Windows 系统托盘。
2. 点击窗口关闭按钮时，默认隐藏窗口，不退出程序。
3. 通过托盘右键菜单可以打开窗口、进入设置或完全退出。
4. 支持双击托盘图标打开快捷面板。
5. 支持设置开机自启动。
6. 支持自定义全局快捷键，默认建议 `Ctrl + Shift + V`。
7. 快捷键再次触发时可以隐藏窗口。
8. 快捷面板失去焦点时可自动隐藏，该行为可以在设置中关闭。
9. 支持记忆窗口位置、尺寸以及上一次使用的界面模式。
10. 支持 Windows 系统缩放与多显示器环境。

### 验收标准

- 关闭窗口后程序仍可通过托盘和快捷键呼出。
- 点击“退出程序”后进程正常结束。
- 快捷键冲突时明确提示，不覆盖其他程序快捷键。
- 多次显示与隐藏窗口不会产生重复窗口或重复进程。
- 自启动配置重启系统后正常生效。

## 2.2 双模式交互界面（P0）

软件采用两种主要窗口模式。

### A. 快捷面板

采用类似 Windows Win + V 的紧凑式浮动界面。

主要包含：

- 搜索输入框
- 最近使用
- 收藏命令
- 命令卡片列表
- 分类筛选
- 复制按钮
- 进入完整管理模式的入口

交互要求：

- 唤出后自动聚焦搜索框。
- `↑ / ↓` 切换选中命令。
- `Enter` 复制当前选中命令。
- `Esc` 隐藏窗口。
- 单击命令卡片即可复制，支持配置复制后是否自动隐藏。
- 卡片显示标题、命令内容预览、标签及背景颜色。
- 长命令支持展开查看完整内容。
- 不允许因为预览截断而导致实际复制内容缺失。

### B. 完整管理界面

采用三栏结构：

**左侧：分类树**

- 展示多级目录。
- 支持展开、收起和拖拽移动。
- 支持创建、重命名和删除目录。

**中间：命令列表**

- 展示选中分类下的命令与工作流。
- 支持多选、排序、拖拽、收藏和批量操作。
- 支持切换卡片模式与紧凑列表模式。

**右侧：详情编辑器**

- 编辑标题、命令内容、注释、标签、颜色等。
- 管理命令所属分类。
- 查看使用记录和相关工作流。
- 提供 AI 自动生成注释按钮。

界面应保持简洁、扁平化，避免过度装饰。

## 2.3 命令采集与保存（P0）

### 手动新增

支持：

- 直接输入命令。
- 从剪贴板粘贴。
- 保存多行命令。
- 添加标题和注释。
- 指定 Shell 类型和所属分类。
- 为命令设置标签和颜色。

### 剪贴板监听

使用 Windows 原生剪贴板事件监听机制。

要求：

1. 可在设置中启用或关闭监听。
2. 检测复制的新文本。
3. 默认不将全部剪贴板内容永久保存。
4. 可选择保留有限数量的临时文本历史。
5. 提供“保存为命令”操作。
6. 支持通过快捷键收藏当前剪贴板文本。
7. 检测重复内容，避免短时间内产生大量重复记录。
8. 可根据来源进程、文本模式或用户配置进行过滤。
9. 排除密码、Token、私钥及其他明显敏感内容，提供手动排除规则。
10. 应用自身复制命令时，不应形成无限监听和重复记录。

剪贴板采集必须考虑隐私安全：默认不采集非文本格式内容，不自动上传剪贴板数据。

## 2.4 分类、标签与收藏（P0）

### 分类

采用多级树状结构。

支持：

- 任意合理层级的目录嵌套。
- 创建、编辑、移动和删除分类。
- 拖拽修改分类顺序。
- 将命令移动至其他分类。
- 删除分类时提供移动其内容、递归删除或取消操作。

### 标签

每条命令可以拥有多个标签。

例如：

`Docker`、`Linux`、`SSH`、`Python`、`部署`、`环境配置`

支持创建、重命名和删除标签，以及按标签搜索和过滤。

### 收藏

支持：

- 收藏 / 取消收藏
- 最近使用
- 使用次数记录
- 手动置顶
- 按使用频率或最近使用时间排序

## 2.5 工作流与步骤编排（P0）

工作流用于将多个相关命令组织为有序执行步骤。

例如：

**Python 项目环境搭建**

步骤 1：创建虚拟环境

```
python -m venv .venv
```

步骤 2：激活虚拟环境

```
.venv\Scripts\Activate.ps1
```

步骤 3：安装依赖

```
pip install -r requirements.txt
```

步骤 4：运行项目

```
python main.py
```

### 功能要求

1. 支持创建工作流。
2. 工作流包含名称、描述和多个步骤。
3. 每个步骤可以引用已有命令或保存独立命令。
4. 同一命令允许被多个工作流引用。
5. 支持通过拖拽调整步骤顺序。
6. 支持为步骤添加独立说明。
7. 支持插入纯文字说明步骤。
8. 支持复制单个步骤。
9. 支持按顺序拼接并复制全部命令步骤。
10. 对不同 Shell、不同执行主机或不同工作目录的步骤，整组复制时应给予提示，避免误认为可以直接连续执行。
11. 暂不支持自动执行。

工作流中的命令应保持其独立 ID，不应通过简单复制命令内容来建立关系。

## 2.6 命令预览、编辑和复制（P0）

### 命令卡片

每张卡片展示：

- 标题
- 命令内容预览
- Shell 类型
- 分类和标签
- 自定义背景颜色
- 收藏状态

### 命令编辑

支持：

- 多行编辑
- 语法高亮
- 自动换行和横向滚动
- 撤销与重做
- 复制部分命令内容
- 添加 Markdown 注释
- 编辑命令标题和说明
- 保存副本

### 复制功能

需要区分以下操作：

1. **单条复制**：复制一条命令的完整原始内容。
2. **文本片段复制**：选中命令中的部分文本并复制。
3. **批量复制**：选择多条命令，按照指定排序进行拼接复制。
4. **工作流复制**：按步骤顺序复制多条命令。
5. **模板复制**：填充参数后生成完整命令。

所有复制操作均不得在未经用户确认的情况下改变命令语义。

对于批量复制，应提供换行分隔或自定义分隔符等选项，并在拼接存在 Shell 语法风险时给予提示。

## 2.7 参数化命令模板（P1）

支持在命令中定义变量，例如：

```
ssh {{username}}@{{host}}
```

或者：

```
scp -r {{username}}@{{host}}:{{remote_path}} {{local_path}}
```

点击模板时，允许用户填写参数，然后生成命令并复制。

要求：

- 自动识别模板变量。
- 提供参数输入表单。
- 支持默认值。
- 支持必填校验。
- 支持保存非敏感参数预设。
- 支持 Shell 类型相关的转义处理。
- 模板原文与实际生成结果分别管理。
- 含密码、Token 等敏感参数时，不保存输入值。

参数模板初期仅生成文本，不自动执行。

## 2.8 搜索与筛选（P0）

支持按照以下信息搜索：

- 命令标题
- 命令原文
- 注释内容
- 分类名称
- 标签
- 工作流名称

支持：

- 关键词搜索
- 模糊匹配
- 搜索结果高亮
- 按最近使用排序
- 按使用频率排序
- 按分类、Shell 类型和收藏状态筛选

建议采用 SQLite FTS5 实现全文索引，并配合简单的模糊匹配机制。

## 2.9 AI 自动生成注释（P0，核心功能）

这是首个正式版本必须实现的 AI 功能。

### 2.9.1 功能目标

用户输入或收藏一条命令后，可以点击“AI 生成注释”，自动分析命令含义。

AI 应能够解释：

- 命令总体作用。
- 命令适用平台或 Shell。
- 重要参数和选项。
- 执行前提和注意事项。
- 可能存在的安全风险。

### 2.9.2 AI API 配置

设置页面增加“AI 服务”模块。

支持用户自行配置：

| 配置项      | 说明                  |
| ----------- | --------------------- |
| API 提供商  | 预设服务商或自定义    |
| Base URL    | 用户自定义 API 地址   |
| API Key     | 用户自己的访问密钥    |
| Model       | 模型名称或标识        |
| Timeout     | 请求超时时间          |
| Temperature | 可选生成参数          |
| 测试连接    | 检查 API 配置是否可用 |

首版优先支持 OpenAI 兼容的 Chat Completions API 协议。

不需要针对每一家模型厂商单独开发完整适配。

API Key 必须使用系统安全凭据存储机制或经过合理保护的密钥管理方案，不以明文形式保存到普通配置文件、数据库或日志中。

支持手动填写模型标识，不强制要求服务提供模型列表接口。

### 2.9.3 AI 注释生成交互

命令编辑页面增加：

**AI 生成注释**

点击后：

1. 获取当前命令原文、Shell 类型及已有说明。
2. 按配置向 AI 服务发送请求。
3. 显示生成中状态。
4. 接收结构化注释结果。
5. 在界面中展示预览。
6. 用户选择“应用”“重新生成”或“取消”。
7. 只有用户确认后，才更新数据库。

对于已经存在注释的命令，不允许直接覆盖原有内容，应提供保留、追加或替换选项。

AI 生成内容应支持人工修改。

### 2.9.4 注释生成格式

要求 AI 尽量返回结构化 JSON。

示例：

```
{
  "summary": "查看所有 Docker 容器，包括已停止的容器",
  "shell": "bash",
  "parameters": [
    {
      "name": "ps",
      "description": "列出容器"
    },
    {
      "name": "-a",
      "description": "显示全部容器"
    }
  ],
  "requirements": [
    "已安装 Docker",
    "具有访问 Docker 服务的权限"
  ],
  "warnings": [],
  "risk_level": "low"
}
```

字段说明：

- `summary`：简短注释，用于命令卡片。
- `shell`：适用的 Shell 类型。
- `parameters`：重要参数的解释。
- `requirements`：执行前提。
- `warnings`：注意事项和风险。
- `risk_level`：`low` / `medium` / `high`。

生成内容可以同时转换为 Markdown 形式，便于预览与导出。

当模型未返回合法 JSON 时，应尝试合理解析或提示用户重新生成，不得保存不完整的错误结构。

### 2.9.5 API 请求规范

系统需要：

- 为命令分析使用独立 Prompt 模板。
- 要求模型以中文生成说明。
- 保持命令原文完整，不随意改写。
- 不执行任何被分析的命令。
- 将命令内容视为待分析数据，而非可信指令。
- 明确告知用户命令内容会发送给配置的第三方 AI 服务。
- 提供请求超时、取消和错误处理。
- 禁止将 API Key 输出到日志。
- 默认不自动发送包含明显密钥、凭据或隐私信息的命令。

所有 AI 功能应通过独立 AI Service 接口调用，避免在 React 页面中直接包含 API Key 或访问模型服务。

### 2.9.6 AI 注释质量要求

AI 生成的注释应该：

1. 以中文为主。
2. 简洁、准确，避免冗长。
3. 对关键参数进行解释。
4. 不编造命令的执行结果。
5. 不确定的部分明确标注。
6. 对删除文件、修改权限、格式化磁盘等高风险命令给出提示。
7. 绝不自动执行被分析的命令。

AI 生成的风险级别只能作为辅助信息，不能替代程序自身的安全检查。

### 2.9.7 验收标准

- 用户成功配置 API Key 后，可以生成命令注释。
- 可以正确处理简单命令、多参数命令和多行命令。
- 生成前后命令原文不变。
- 断网或 API 出错时不会丢失本地数据。
- 没有配置 API 时，其他功能均正常使用。
- 密钥不会通过前端日志或数据库导出泄露。
- AI 结果必须经过用户确认才会写入注释。

## 2.10 数据存储、导出与备份（P0）

### 本地数据库

使用 SQLite 保存：

- 命令
- 分类
- 标签
- 工作流
- 工作流步骤
- 注释
- 命令使用统计
- 应用设置

系统采用数据库版本迁移机制，支持后续功能升级。

### 导入导出

支持：

- JSON 完整导出
- JSON 完整导入
- Markdown 命令文档导出
- YAML 导出（P1）
- 本地数据库备份与恢复

导出结构应包含 Schema Version，保证后续格式升级兼容性。

### 数据可靠性

要求：

- 使用数据库事务保障关联数据一致性。
- 避免重复保存和意外覆盖。
- 删除操作提供确认和必要的撤销能力。
- 提供数据备份与恢复。
- 数据库迁移失败时不能破坏已有数据。

# 三、技术架构

## 3.1 推荐技术栈

| 层级             | 技术                    |
| ---------------- | ----------------------- |
| 桌面应用框架     | Tauri 2                 |
| 前端框架         | React + TypeScript      |
| 构建工具         | Vite                    |
| UI 样式          | Tailwind CSS            |
| UI 组件          | shadcn/ui               |
| 状态管理         | Zustand                 |
| 树状拖拽         | dnd-kit                 |
| 命令编辑器       | CodeMirror 6            |
| 本地数据库       | SQLite                  |
| 全文检索         | SQLite FTS5             |
| 系统原生功能     | Rust + Windows API      |
| AI 服务          | OpenAI 兼容 API         |
| 前端测试         | Vitest                  |
| 桌面端自动化测试 | 依据 Tauri 兼容工具选型 |

依赖具体版本应在开发时验证兼容性，并通过锁文件固定。

## 3.2 架构原则

必须遵循：

1. 前端 UI 不直接操作数据库文件。
2. 数据库操作集中在独立 Repository 层。
3. 所有持久化写操作通过统一服务接口处理。
4. AI API 的密钥管理与网络调用在后端进行。
5. 系统托盘、剪贴板与全局快捷键由独立系统服务负责。
6. 工作流、分类和命令应分别定义模型。
7. AI 功能可以独立关闭或替换提供商。
8. 核心业务逻辑不能依赖具体 UI 组件。
9. API Key、剪贴板和日志处理应采用最小权限原则。

# 四、UI 与用户体验规范

## 4.1 设计原则

- 简洁、紧凑、现代化。
- 信息密度适中。
- 尽量避免复杂弹窗。
- 优先支持键盘操作。
- 支持浅色和深色主题。
- 命令内容使用等宽字体。
- 不使用大量无意义动画。
- 所有复制、保存、删除操作有明确反馈。

## 4.2 命令卡片颜色

允许用户设置自定义背景颜色。

预设颜色可以包括：

- 蓝色：远程连接
- 绿色：环境管理
- 黄色：配置操作
- 紫色：Git 与版本管理
- 灰色：普通命令
- 红色：用户标记的重要或危险命令

上述颜色只是默认示例，不强制绑定具体分类。

背景色应与文本颜色自动适配，确保可读性。

## 4.3 AI 注释展示

AI 生成内容分为两层：

**简短注释**

显示在命令卡片或命令标题下方，用于快速理解命令用途。

**详细说明**

在详情编辑器中展示，包括参数说明、前提条件、注意事项和风险提示。

这样能够保留快捷面板的紧凑特性，同时提供足够的信息。

# 五、实施计划

采用逐阶段开发方式。每阶段需要保证项目可以正常运行，并完成对应功能验收后再进行下一阶段。

## 阶段一：项目初始化与桌面基础功能

**目标：建立稳定的桌面应用框架。**

实施内容：

1. 初始化 Tauri 2 + React + TypeScript 项目。
2. 集成 Tailwind CSS、UI 组件和状态管理。
3. 建立基础目录结构。
4. 实现系统托盘图标和菜单。
5. 实现关闭窗口隐藏到托盘。
6. 实现全局快捷键注册和窗口唤出。
7. 实现快捷面板和管理界面的基本切换。
8. 实现应用设置持久化。
9. 实现本地开发启动与 Windows 安装包构建。

**交付标准：**

应用可以在 Windows 上正常启动、隐藏、呼出和完全退出。

## 阶段二：命令数据库与基础管理

**目标：实现可长期使用的命令收藏管理能力。**

实施内容：

1. 建立 SQLite 数据库和迁移机制。
2. 实现 Command、Category、Tag 等核心数据模型。
3. 实现命令增删改查。
4. 实现目录树管理。
5. 实现标签与收藏。
6. 实现命令颜色设置。

8. 实现单击复制和复制反馈。
9. 实现搜索和筛选。

**交付标准：**

不依赖网络，可以完成命令保存、分类、搜索、编辑和复制；重启后数据正常保留。

## 阶段三：剪贴板管理与快捷面板优化

**目标：实现接近 Win + V 的使用体验。**

实施内容：

1. 接入 Windows 剪贴板监听。
2. 实现剪贴板文本检测和去重。
3. 实现临时历史与永久收藏的区分。
4. 实现快捷收藏当前剪贴板文本。

8. 实现快捷面板自动隐藏等行为设置。
9. 验证剪贴板监听与应用自身复制的兼容性。

**交付标准：**

用户能够通过快捷键快速呼出界面，并在不打开完整管理窗口的情况下找到和复制命令。

## 阶段四：工作流与命令模板

**目标：支持复杂命令步骤管理和复用。**

实施内容：

1. 实现 Workflow 和 WorkflowStep 数据模型。
2. 实现创建、编辑和删除工作流。
3. 实现工作流步骤新增与排序。
4. 实现步骤引用已有命令。
5. 实现单步复制与完整流程复制。
6. 实现工作流注释。
7. 实现参数化命令模板解析。
8. 实现变量填写、校验和命令生成。
9. 实现 Shell 相关的参数转义策略。
10. 对跨平台、跨 Shell 工作流增加提示机制。

**交付标准：**

能够将多条命令组织为可维护的流程，并按需要复制其中的步骤或生成模板命令。

## 阶段五：AI 自动生成命令注释

**目标：完成首版核心 AI 功能。**

6. 实现命令解释 Prompt。

8. 实现 AI 注释生成与预览。

10. 支持已有注释保留、追加或替换。

# 六、后续版本功能（暂不实施）

以下功能只需要在架构上预留扩展能力，不要在首版中提前开发复杂逻辑。

## 6.1 AI 自动分类

AI 读取命令内容，推荐所属目录和标签。

支持用户确认后批量应用。

## 6.2 AI 重复命令识别

识别语义相同、参数不同的命令，推荐合并为参数模板。

## 6.3 AI 工作流识别

分析命令间的关联，推荐将相关命令组合为有序工作流。

## 6.4 自然语言搜索

支持通过自然语言描述检索命令。

例如：

“从 Linux 服务器下载文件到 Windows 本地。”

AI 可推荐对应 SCP 命令或命令模板。

## 6.5 MCP 接口

通过 MCP 使 Codex、Claude Code 等外部 AI 编程工具可以在明确授权下：

- 搜索命令
- 读取命令内容
- 查询已有工作流
- 推荐命令分类
- 生成候选注释
- 提议修改命令库

对于写入、删除和批量修改操作，必须设计合理的权限和确认机制。

## 6.6 命令知识库

将命令、错误信息、解决方案、使用场景和工作流关联为结构化知识条目。

## 6.7 可选同步机制

后续可评估文件同步、WebDAV 或 Git 等方式进行跨设备数据同步。

同步必须处理数据冲突和敏感信息保护。

# 七、AI 编程工具实施要求

由于该项目计划主要由 AI 进行编码，开发过程中需要遵守以下要求。

## 7.1 分阶段开发

严格按照实施计划推进。

每次仅处理当前阶段或明确指定的任务，不应一次性重构整个项目。

每阶段结束后必须：

1. 确认编译成功。
2. 运行对应测试。
3. 检查功能是否满足验收标准。
4. 修复发现的错误。
5. 更新相关文档。
6. 总结已经实现和尚未实现的功能。

## 7.2 代码质量

- 使用 TypeScript 严格类型检查。
- Rust 模块保持职责清晰。
- 禁止将大量业务逻辑放入单个 React 组件。
- 避免不必要的全局状态。
- 尽量通过接口解耦各服务。
- 对关键业务逻辑编写测试。
- 尽量采用成熟的依赖和规范。
- 避免添加暂时用不到的重型框架。
- 不要为了赶进度而保留无法运行的占位代码。

## 7.3 数据安全

- API Key 不得硬编码。
- 不得将敏感信息输出到日志。
- 不得将未确认的 AI 结果直接写入数据库。
- 不得自动执行用户收藏的命令。
- 不得默认将全部剪贴板内容发送给 AI。
- 对危险操作提供确认。
- 数据模型和迁移必须支持升级和回滚或可靠恢复。

## 7.4 文档维护

项目中至少维护以下文档：

```
docs/
├── architecture.md
├── database-schema.md
├── feature-list.md
├── implementation-plan.md
├── development-progress.md
```

- 已完成功能

**最终产品定位：**

Pata Commands 是一个以快速复制为入口，以结构化命令管理为核心，以 AI 自动注释为增强能力的轻量级 Windows 开发者工具。

它应当既能够像 Win + V 一样随时唤出，也能够像一个长期维护的个人命令知识库一样持续积累开发经验。
